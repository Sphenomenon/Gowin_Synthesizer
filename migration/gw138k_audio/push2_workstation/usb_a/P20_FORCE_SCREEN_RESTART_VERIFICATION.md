# P20 力度校准与 Push 旧帧立即重启

状态：源码、定向仿真、完整 CPU/音频回归、综合/布局布线和 SRAM 下载已完成。板上 UserCode 为 `0x0000F9B7`；力度听感和 Push 屏幕交互延迟等待用户实体确认。

## 力度映射

P20 对所有非零 pad 力度增加 28，并在 127 饱和：

| Push 原始值 | 音频与显示采用值 |
|---:|---:|
| 0 | 0 |
| 1 | 29 |
| 2 | 30 |
| 64 | 92 |
| 99–127 | 127 |

该映射同时作用于 Note-On、带 note 的 poly-aftertouch、无 note 的 channel pressure，以及供 Push UI 使用的 `last_velocity`。因此用户指出的同一次力度输入不再按 `002` 处理，而是精确按 `030` 处理。零力度保持零，避免把释放或零压力变成非零事件。

## 屏幕传输调度

Push 2 公开显示协议没有区域地址或局部提交命令。P20 继续只发送文档规定的 16 字节帧头和 640 个 512 字节像素包，不试验保留格式。

P19 的问题是：离散操作发生在保活帧传输期间时，固件先传完已经过时的旧帧，再传新帧，两帧相加接近一秒。P20 每传四个像素包轮询一次 MIDI；若模式、音色、效果、路由或持键状态已经不同于当前传输帧，就放弃尚未发送的旧帧尾部，并以最新状态从正常帧头立即重启。未完成的旧帧不会被 Push 显示。

连续 `note_velocity` 不触发重启。压力在一帧传输期间持续变化，如果每次变化都中止，就可能一直无法提交任何完整帧。压力仍实时进入音频，Push 屏幕在下一次能够完成的画面中显示快照。

这属于传输端的旧帧中止和重启，不是设备协议层的区域刷新。J18 Full-Speed 链路发送一个完整帧仍约需 450 ms；实体目标是去掉等待旧帧尾部的额外一帧，使离散操作在约一个新完整帧内出现。

- `p20_force_mapping/simulation.log`：Note-On `64` → `92`、poly-aftertouch `2` → `30`、零值、饱和值和 channel pressure `23` → `51` 全部通过。

## 实体验收

1. 用此前屏幕或听感判断为 `002` 的同样按压力度，确认现在显示并作用为 `030`。
2. 等屏幕静止保活开始后，再切换模式、音色、效果或路由并按/松 pad，确认画面不再等待旧帧传完后才排新帧；预期约一个完整帧周期，不承诺 30 fps。

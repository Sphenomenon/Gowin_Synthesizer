# P19 Push 屏幕完整帧保活候选

状态：P19 已完成固件、综合/布局布线和 SRAM 下载。用户确认静止屏幕保活正常，P18 已通过的 poly-aftertouch 连续变化保持正常；随后复测确认操作刷新仍接近一秒，因此交互延迟未通过并由 P20 取代。用户要求的原始力度 `002` 映射为 `030` 也由 P20 实现。

## P18 实测与原因

P18 在 UI 状态变化时立即发送一个合法完整帧，静止时不再重复传输。用户实测压力连续变化正常，但 Push 屏幕在无操作时自动黑屏、有操作后重新亮起。

Ableton 官方手册规定，Push 2 在两秒内未收到新完整帧时将屏幕变黑；只有接收完 16 字节帧头后的 640×512 字节像素数据才显示新帧。协议没有区域地址或局部提交命令，其它数据长度属于保留格式。因此本阶段没有发送短帧或试验未公开命令，也没有修改 Push 固件。

## P19 改动

- 保留 P18 的事件驱动发送：control/options、held mask、note/velocity 变化时，显示链路空闲后立即发送新完整帧。
- 从上一帧完成时刻开始计时，UI 静止满 1000 ms 后发送一个合法完整保活帧。按当前约 450 ms 的传输时间，相邻完整帧完成间隔约 1.45 s，低于 Push 的 2 s 黑屏门限。
- 空闲仍每轮轮询 MIDI并延时 1 ms；传帧期间每 4 个屏幕包轮询 MIDI、每 32 包服务灯光。压力、灯光和音频不等待保活计时。
- 不修改 P18 poly-aftertouch 初始化、压力映射、HDMI、DDR、C 模式 32 声部、P10 效果链或 P2 低音。

局刷没有作为实现选项：当前公开协议要求完整帧，短帧不能提交到屏幕。达到 30 个完整画面每秒仍需要 J18 上经过验证的 USB 2.0 High-Speed 物理层；P19 继续使用现有 Full-Speed USB-A，不使用 CH569。

## 验证

- `production_usb_firmware_test.log`：热插拔、DATA toggle、帧中 MIDI、完整 640 包帧、首次 dirty、1000 ms 保活边界及再次 dirty 立即调度通过。
- `cpu_audio_sim_172408_225932/simulation.log`：3696 个音频帧、3574 个非零帧，A/B/C、五音色、FX7、expression、路由、释放和精确 48 kHz 通过，无 audio fault。
- P19 与 P18 的 Push aftertouch/映射 RTL 哈希相同，因此没有重复运行已经通过并经实体确认的压力测试。

这些是离线固件和 RTL 结果，不代替本次实体屏幕验收。

## 实体验收

1. Push UI 静止至少 5 秒，确认屏幕保持原画面，不再自动黑屏或周期闪烁。
2. 静止后操作模式、音色、效果或路由，确认新画面仍在一个完整帧周期附近出现，没有恢复到持续旧帧排队的近一秒延迟。
3. 按住 pad 改变压力，确认 P18 已通过的连续声音变化不受影响；同时检查灯光、HDMI、耳机、C 模式、效果链和低音。

用户确认本版本静止保活通过，但操作变化仍接近一秒。P19 保留为可回退版本，不再作为屏幕交互延迟的通过版本；P20 在不使用协议保留格式的前提下加入旧帧中止与立即重启，并加入力度 `002` → `030` 映射。

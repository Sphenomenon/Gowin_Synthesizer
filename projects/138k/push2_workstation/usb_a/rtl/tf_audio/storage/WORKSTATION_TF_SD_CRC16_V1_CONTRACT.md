# Opt-in SD data CRC16

`VERIFY_DATA_CRC` defaults to zero in the maintained sector, file, direct-native and direct-runtime owners. A new DIRECT candidate must select `1` explicitly and compile `workstation_tf_sd_crc16_v1.sv`. Existing divider defaults remain unchanged, including `SPI_CLK_DIV_FAST=12`. Enabling integrity checking does not fix or qualify sustained playback supply.

The first-party checker consumes the actual maintained SPI session's byte events: indexes 513 through 2 are exactly 512 payload bytes, followed by CRC high byte at index 1 and low byte at index 0. The polynomial is `0x1021`, initial state zero, MSB first and no final XOR. The token, R1 and CRC bytes are excluded from the payload CRC. Unexpected, missing, repeated or out-of-order byte indexes cannot produce a valid verdict. Each new accepted sector request clears the prior verdict; a late previous result cannot authorize a later sector.

The native sector owner applies the verdict only on its existing `spidone`. It retains the complete transaction, including both CRC bytes and the original one-byte CS-high release. Valid CRC preserves the original `done`. An invalid or incomplete CRC produces sticky `read_error`, code `3`, and `FAULT`, with no `done` or automatic replay. Existing R1 and token failures keep their prior codes. The file owner maps this through its existing terminal transport-failure path and invalidates the session. Recovery still needs the explicit whole-file-owner reset; this change does not add a remount command or globally reset the basic audio schedule.

STOP remains a file-owner cancellation. It immediately fences file output, blocks new data requests and waits for an outstanding payload, CRC and CS release to finish. The CRC checker never cancels or resets the SPI session. A CRC failure during cancellation is a failed stop, rather than a successful drain acknowledgment. Tests of cancellation must use the real file owner's `stop`; the sector owner has no STOP input, and reset abort is not a substitute.

Payload bytes remain streamed before the final CRC verdict. A corrupt sector can already have supplied a prefix to the downstream byte/PCM path before the session is invalidated. This is integrity detection and session failure, not sector atomic publication or proof that no corrupt sample was consumed. Such a claim needs validated-sector buffering or a separate bounded consumption proof.

The prior two provenance manifests, vendor sources and frozen candidates retain their exact bytes. `workstation_tf_sd_crc16_v1.adaptation.json` separately locks the four prior source identities and each reversible edit. `tools/workstation_tf_sd_crc16_provenance.py` verifies current source identities, strictly restores the prior identities in memory and rechecks the original derivation. Reconstruction is used only for validation; production builds consume the maintained sources directly. Historical sector/file wire regressions accept this source change only with explicit `--direct-crc-source-adaptation`; their DUT parameter remains zero and their old synthetic CRC bytes do not become CRC-valid evidence.

New CRC wire tests need correctly calculated sector CRC values and an independent oracle such as Python `binascii.crc_hqx(payload, 0)`. They must corrupt payload, high CRC, low CRC and absent CRC independently and check complete payload/CRC/CS drain before the success/error terminal. Separate STOP cases cover the payload tail, both CRC bytes and CS release. Simulation is not physical SD integrity, throughput, routed timing or board acceptance.

# C1 黑屏与 B3 出图版本对照（2026-10-27）

用户反馈当前 HDMI“有信号但无画面”。本轮直接对照 C1 与历史可出图 B3 的实际编译输入、P&R 命令、约束、时钟路由，并只读当前 C1 已有 GAO。**当前阻塞已确认是 DDR 校准未完成；不是再次遗漏三项专用资源定位。首次校准失败的底层原因仍未确定。**

## 身份与范围

- 初始问题候选：`C11027C1`，位流 SHA256 `91101332be8d8d5ac3511cc36227d77ab0fe2511f5869efb90c657b55ee1386a`，来源 `custom138k-native-integration-20261027-a26`。后续授权实验结束时 SRAM 为 B3，见下文。
- 历史对照：`C11026B3`，位流 SHA256 `a901738a4e07eb777cbc32eb571179e93ebae86e8488e573d4b65696e100011c`。用户曾确认有画面但快速闪烁，不是稳定显示验收版。
- 本次三次抓取分别开始于 13:13:04、13:13:07、13:13:10（Asia/Shanghai），每次前后独立读取均为设备 `0x0001081B`、UserCode `0xC11027C1`。
- 仅使用既有 `capture_ddr_jtag.py`，核对 GAO 身份、WINUSB OPEN、全部 READ_RAM 与每次 1,024 样本；没有烧录、复位、操作 Flash、断电或新综合／P&R。工具保留旧的 `jtag_capture_20261026_*` 目录命名，实际抓取日期以 `started_at` 为准。

## 业务源码与实现差异

两版工程启用的 **230 项输入集合相同，225 项字节相同**。不同的五项只有：

1. `constraints/custom_138k.cst`：增加上述三条已在 B3 物理阶段存在的定位。
2. `native_bluetooth/ble_protocol_command.v`。
3. `native_bluetooth/bt_gatt.v`。
4. `native_bluetooth/bt_verilog_core.v`。
5. `rtl/bluetooth/workstation_bluetooth.sv`。

HDMI 时序／取行／渲染、DDR 平台／复位 guard／BIST、仲裁／队列／地址图、DDR vendor IP、音频与顶层业务输入均相同。变化不涉及新增 DDR 客户端或帧缓冲分区。

但**物理布局并不相同**：B3 复用 E4 网表及已布线数据库做增量 P&R，C1 则重综合并做完整非增量 P&R。约束及源码相同不能推出训练相关路径的布局完全相同；目前没有证据把全部差异归因于 BLE，也不能仅凭 C1 STA 通过认定 DDR 实际训练已通过。

授权对照后进一步比较两份实际实现后的 `.vo`：`u_memory/` 子树各 **9,131 个实例**，实例名集合、原语类型、全部参数相同；端口连接也仅有两项一致的网络重命名（`n32_3_483→n32_3_485`、`memory_clk_376→memory_clk_378`），没有其他差异。这是限定范围的结构比较，不是形式等价或物理位置相同的证明。

两份 SDF 中涉及 DDR 的 **47,678 条互连端点集合相同，但布线延时不同**。例如 lane1 `oserdes_dq_r_18_s0/Q→oserdes_gen[2].u_oser8_mem/D2` 的最大报告互连延时从 2.451 ns 变为 5.319 ns；该单项差异不是违规或训练失败的独立证明。它进一步支持用同一 C1 网表、成功 B3 物理参考做受控实验，而不是先修改 BLE／仲裁逻辑。摘要与输入哈希见 [hdmi_ddr_implementation_comparison.json](ae350_resources_20261027/hdmi_ddr_implementation_comparison.json)。

## 实板状态：视频时钟在跑，DDR 数据路径未启动

三次 C1 抓取的全部样本均为 `memory_flags=0xC0`、`video_flags=0x26`，观测信号在各捕获窗口内均无跳变：

| 状态 | C1 当前 | B3 历史成功窗口 |
|---|---|---|
| DDR／视频 PLL 锁定 | 是／是 | 是／是 |
| DDR 校准完成 | **否** | 是 |
| BIST 完成／失败 | **未完成／未置失败**，不是 BIST 通过 | 完成／未失败 |
| 有效前台帧 | **无** | 有 |
| 像素复位释放 | 是 | 是 |
| 取帧复位释放 | **否** | 是 |
| 标志组合 | `0xC0 / 0x26` | `0xEB / 0x2E` |

实际 `ddr3_platform.v` 只有在 PHY 校准完成后才释放 UI 复位；`hdmi_display.v` 的显示数据复位又依赖该复位。像素／同步路径可独立运行，所以此状态正好允许**显示器锁定信号但看到黑色光栅**。当前首先卡在校准，尚未进入正常取帧，不能把未发生的取数错误解释成“仲裁正常”或将黑屏直接归为显示带宽不足。

HPD 样本为 0，与 B3 可出图时相同，本链路不以它门控；不据此否定用户已接入显示器或重归因接线。

## B3 并非每次直接加载都能出图

[2026-10-26 闪烁报告](WORKSTATION_HDMI_FLICKER_20261026.md#后端部署与暖启动对照) 及原始抓取记录了同一份 B3 位流的两种状态：

- 10:40，从隔离 DDR B2 切到 B3：`0xEB / 0x2E`，随后用户确认出图。
- 11:57，直接恢复同一 B3：抓取 05／06 均为 **`0xC0 / 0x26`**，与当前 C1 完全相同。
- 11:59，再先运行 B2、后加载同一 B3：抓取 07／08 恢复 `0xEB / 0x2E`。

因此，初始化／暖重配置前态依赖是已存在的问题，不是本轮才首次出现。C1 于 12:42 从 `C1102515` 直接加载，未经过 B2；这与 B3 历史失败模式相容，但本轮未执行 C1 的启动前态 A/B，**还不能认定具体初始化机制相同，也未排除新物理布局的影响**。

两版相同的 `ddr_recovery_guard.v` 没有“PLL 持续锁定但首次校准始终未完成”的超时重训分支。这能解释为什么失败后一直停住，不证明首次训练为何失败；不应靠跳过校准／BIST、强制就绪或无界重试掩盖它。

## 授权后的同板启动顺序对照

用户随后明确允许 HDMI 排查继续写入 SRAM，无需重复询问；不包含 Flash 或断电。本节是后续实测，不改写前述只读检查的范围。两组实验均复用已有精确位流、相同 JTAG 端点及抓取工具，持有板卡锁，下载后独立核对 UserCode；未新综合／P&R、未操作 Flash、未断电。

| 实验及时间（2026-10-27，Asia/Shanghai） | 阶段 | 捕获窗口 | 结果 |
|---|---|---:|---|
| C1→B2→C1，13:39:22–13:39:54 | 初始 C1 | 1 | `0xC0 / 0x26`，校准／BIST／前台帧未就绪 |

每窗口 1,024 个样本。B2 精确位流 SHA256 为 `b1160972329e51428c14e16cb46d641359a35e8d76852506b07802591f55480a`；B3／C1 与上文相同。B3 的 `underrun_seen` 已置位，它是历史粘滞标志，不代表测得当前欠载频率；未据此宣称闪烁消失。尚无本次显示器实际画面的新确认。

**结论收窄：B2 预初始化不是 C1 的修复。**同板、相同 B2 前置流程下，B3 成功而 C1 失败，必须继续区分 C1 新实现的退化；不能只归为旧的暖启动前态依赖。13:42:14 实验结束后将 B3 留在 SRAM，保留一个 DDR／显示数据路径已就绪的临时对照；不是资源优化或 BLE 功能的最终交付，也不改变 Flash。

原始记录位于 `out/hdmi_startup_ab_20261027/` 及其 `b3_control/`；受版本管理的摘要与原始证据哈希见 [hdmi_startup_ab.json](ae350_resources_20261027/hdmi_startup_ab.json)。

## 下一步与回退

单独准备新身份 `C11027C2`：复用 C1 已综合的 a26 优化网表、完全相同的物理 CST／SDC 和 16-bit GAO，仅更换 UserCode／GAO ID，并以 B3 实际成功的 `.p/.pr` 为增量 P&R 参考。没有重综合、放松时钟／例外、删除功能或修改 vendor／冻结基线。实验输出为 `out/workstation_resource_a26_20261027_c2_incremental/`，完整输入哈希在其 `physical_inputs.json`。这是验证物理实现影响的开发实验，**不是已经生效的修复**；结果与实际复用程度需以工具日志、物理门禁及上板为准。

### C2 结果：增量路由失败，不部署

2026-10-27 13:48:03 开始，14:47:22 工具退出 1，耗时约 59 分 19 秒。跳过综合后确实进入增量重布线；一次只读堆栈检查落在 `Route::incRerouting→DesRoute::mazeRouteByDes`，不是等候板卡。最终两次 `DesRoute failed`，明确报错 **`PR0004: 1785 unrouted nets`**。没有 `.fs`，没有执行 C2 SRAM 写入；后续物理门禁因缺少位流未运行，不把它们算通过。

B3 物理库跨到 C1 新网表的这次复用失败且比 C1 全量 P&R 更慢，因此不把它推广为加速方案，也不把失败资源摘要算作节省。机器摘要见 [hdmi_c2_incremental.json](ae350_resources_20261027/hdmi_c2_incremental.json)。板上继续保留之前的 B3，不因新工具生成了 `.vo` 就当成可部署实现。

下一受控探针 `C11027C3` 改用 **C1 自己已完整布线的 `.p/.pr`**，业务网表／CST／SDC 不变，只将原 16-bit GAO 换成 DDR 平台复位／PLL 使能、DLL 锁定、PHY ready、写训练／读校准／眼图扫描阶段及四 lane 读校准完成位。仍使用一个 16×1024 观察缓存，不为诊断引入新的业务 RAM。既有抓取工具新增显式 `workstation-ddr-training-16-v1` 解码；原始异步控制位不冒充相干快照。这一轮目的是定位训练停在哪一步，不预设超时重训、修改仲裁或继续盲扫布局参数。源实现与物理通过、板测仍分开。

已有精确 B3 位流仍可作为临时回退，但历史证据已表明直接加载 B3 也可能黑屏，不能承诺“回到 B3 一定恢复画面”。真正修复仍须保留校准、BIST、显示实测及 BLE 功能门禁，避免先改仲裁、无依据叠加重试或盲加物理约束。

机器可读对照及证据哈希见 [hdmi_c1_b3_comparison.json](ae350_resources_20261027/hdmi_c1_b3_comparison.json)。完整 230 项哈希比较、GAO 配置、抓取、命令与身份日志保留于 `out/hdmi_c1_b3_compare_20261027/`。当前 C1 **HDMI 实屏未通过**，不把先前离线通过或 BLE 通过提升为整机硬件通过。

**演奏指引的时间分辨率与 High-Speed USB 内存预算**

日期：2026-10-20。承接用户提出“原音乐每秒采四个点即可用于指引”和后续自有板 High-Speed USB 的新约束。核对已有源码、已保存板测记录与官方资料；未改 RTL／固件、未跑新综合或操作硬件。

**结论**

“指引只需要离散音符事件”的方向成立，但必须区分音频采样、分析帧率、事件密度、传输批次与界面刷新。每秒 4 个波形采样无法保留音乐音高；每秒 4 次音高判定可用于粗略慢旋律，但会漏掉两次判定之间的短音或重复击键。只把已经算出的结果每秒发 4 次，不能释放 CNN 大缓存。

建议保留当前 22.05 kHz 单声道分析输入，优先改成低成本连续起音检测＋稳定段稀疏推理＋起音附近精细判断。指导队列只保存音符变化和重新起音，界面可低频更新，按键与实时控制仍及时处理。若愿意接受先分析、后演奏，分析缓存与 TASLP 状态存储可以探索跨阶段复用，收益可能比单纯降低输出帧率更大。

High-Speed 并不要求按速度比例扩大 CPU RAM。建议暂时保留 64 KiB CPU 共用 RAM，把新增包缓冲单列；上一份第一轮 45 块节省目标中的 USB 64→32 KiB（16 块）先撤出优先预算，其余五项仍可作为约 29 块的未实施目标。HS 主机／固件选定后再测栈和吞吐决定缩容。

**源码核对：当前已经做了什么**

| 层次 | 当前实现 | 对“4 次／秒”的含义 |
|---|---|---|
| 音频输入 | 44.1 kHz 先适配 48 kHz；前端混成单声道，再按 147/320 转为 22.05 kHz | 可进一步研究分析音频降采样，但不能降到 4 Hz；更改训练输入率不是简单改一项参数 |
| CQT 时间网格 | 初始 hop=256，22.05 kHz 下约 86.13 帧/s，11.61 ms/步；跨八度按降采样相应缩 hop | 这是音高特征的时间密度，区别于音频采样率 |
| CNN 特征缓存 | 7×88×32 个 16-bit 值，共 38.5 KiB，PNR 32 块 | 存的是局部依赖行窗；不是 172 帧全窗。只改 FRAME_LIMIT 或输出抽帧不会按 86/4 比例缩小它 |
| 权重缓存 | PNR 8 块 | 权重尺寸不随输出帧率改变 |
| 解码 | 88 个音高＋休止的 Viterbi 路径；后端按稳定音高段／新的 onset 产生 score step | 当前是单音旋律序列，不是分离录音中各乐器的独立音频轨 |
| Push 跟奏 | 172×7 bit 有界音符队列，弹对目标才推进；接口是 score_note，没有每帧时长字段 | 已经不需要把全部稠密结果交给指引 UI，也不是按 86 Hz 自动切灯 |

源码顶部部分阶段注释已经过时，本表依据实际实例参数、数组、状态机和路径判断。前端、CQT、Viterbi 这三份活动文件与 timing_p27 暂存快照逐字节相同。

**为什么 4 Hz 只能用作部分环节**

- 若指原始波形采样，每秒 4 点的 Nyquist 上限仅 2 Hz，音乐音高信息不能保留。例如 440 Hz 的正弦在每 250 ms 的等间隔采样中会落到相同相位，无法分辨该音高。
- 若指每 250 ms 取一次音高快照，0.06–0.16 s 的短音可能完全位于 0 和 0.25 s 两次快照之间。120 BPM 的十六分音符间隔为 125 ms，固定四次快照不能保证记录全部音符。重复同音尤其需要 onset，单看持续音高状态会合并掉重新击键。
- 若每 250 ms 分析一整段音频，并输出段内全部事件，这可以成立，但段内仍要保留足够时间分辨率；外部交付频率是 4 Hz，内部不是只保留四个音高快照。
- 若只是界面四次刷新／秒或批量传事件，可以保持全部事件；当前跟奏的目标推进也不必被固定为 4 Hz。同步播放时批量传输要提前缓存并带时间戳，不能把过期事件集中延迟发送。

不能直接把现有 CNN 的输入时间步从 11.6 ms 改成 250 ms 后继续声称数值／音质等价。时间卷积所观察的时间跨度、起音头、持续判定和最短音符门限都会改变，需重新验证，必要时重训。仅抽取最终输出则没有这项模型变化，但也基本没有计算／大缓存节省。

**适合本工程的优化选择**

1. 保留模型当前输入采样率和连续前端，界面显示、调试报告可独立低频刷新。这很容易隔离，但 BSRAM 收益小。
2. 增加低成本起音检测，在长稳定段降低昂贵推理调用密度，在起音附近保留短时细分辨率。需要为音频上下文建立环形缓存，并验证混合音乐、弱起音、连奏、快重复音；这不是直接跳过若干旧 CNN 帧即可成立的优化。
3. 如果用户实际只需一个主旋律／跟奏序列，可离线比较更小的音高跟踪模型、CQT＋谐波评分＋起音检测、现有 CNN。先用短音／重击／快速音阶／伴奏干扰测试确定准确率，再决定是否替换整套网络。不能把主旋律提取称作多乐器分轨。
4. 更大的资源方向：先扒谱，将事件序列写 DDR，再进入演奏阶段。把 CNN 的特征 32＋权重 8 块作为共享存储池候选，与新音源的状态／系数存储按阶段复用。两阶段不同时占用同一 bank，切换时重装数据。只有显式复用同一物理 RAM 才节省；停 clock 或 UI 关闭不会释放配置资源。实际收益由时钟、端口、bank 数与切换协议决定，暂不预记为已省 40 块。若仍要求边弹边扒谱，这个互斥阶段假设不成立。

**High-Speed USB：要分别核算两端**

仓库已有 `projects/25k/example/USB3300_HS`，是 USB3300＋60 MHz 8-bit ULPI 的 HS CDC **Device**，并非 HS Host 或最终 MIDI＋PL 复合设备。2026-10-16 记录显示主机确认 480 Mbps 枚举，56 块、21248 B 回环逐字节通过，使用 2048 B echo FIFO；没有证明持续满速吞吐。

138K 当前工作站是 Full-Speed **Host**。当前 Host TX/RX FIFO 已各有 512 B；普通 MIDI 端点的固件校验仍只接受 8/16/32/64 B 最大包。直接连接 HS-only 描述符的板子不能只换 PHY；138K Host 链路、枚举／端点校验、包握手与调度都要支持 HS，最终设备端也需落实 MIDI＋PL 业务。USB3300 是 PHY，本身不替代上述 Host 控制器。

25K 的设备 FIFO 计入 25K 资源，138K 的 Host FIFO／CPU 存储计入 138K。双方之间的 Bulk 最大包在 USB 2.0 High-Speed 为 512 B，Full-Speed 为不超过 64 B；此差异不意味着要把全部 CPU RAM 放大八倍或四十倍。

**RAM 应分为三类**

| 类型 | 建议 | 原因 |
|---|---|---|
| Host CPU 代码、数据、栈 | HS 集成阶段先保留现有 64 KiB；之后按实测决定 48/32 KiB | 主要随固件、描述符、设备数、类驱动和软件队列变化，不随线速同比增长 |
| 片内包缓冲、时钟桥接、重传副本 | 对 138K 新 HS 路径先留 8–16 KiB 设计预算 | 这是含多个端点／双缓冲的初始预算，不是协议最低值或已有净增；按常用 16 Kibit 数据配置理想约 4–8 块 BSRAM，独立 bank／端口映射可能更多 |
| 屏幕、PCM、大文件等长数据队列 | 大环形缓冲放共享 DDR，片内只留数包／短时预取 | 避免整帧显示、长音频或固件上传数据挤占片内 RAM |

若仅传 MIDI／控制／灯光，不追求持续满速，双向各两包 512 B 的载荷总量只有 2 KiB，再加控制／状态／跨域余量。8–16 KiB 是更宽松的工程预留，不能解释为每个端点必需这么多。

每方向应依据业务峰值和最坏服务空档计算：

`buffer >= payload_bytes_per_second × worst_service_gap_seconds + packet_reserve`

还要计入重传与已受理未完成的数据。以 48 kHz、双声道、24-bit PCM 为例，载荷为 288000 B/s；2 ms 服务空档对应 576 B，另加一包 512 B 即 1088 B 的简单起算量。实际配置需留更多余量并验证仲裁，而不是按 480 Mbps 的物理线速为每个业务机械配置大缓存。若确实要持续几十 MB/s，缓存和 DMA／CPU 架构需按那个业务重新设计。

支持 HS 是链路能力；若只传 MIDI，数据量仍小。数据搬运应尽量交给包引擎／DMA，CPU 管枚举和控制，避免逐字节轮询成为吞吐瓶颈。这里是架构建议，当前未实现新的 HS Host／DMA。

**对上一轮预算的修订**

- 原第一轮 45 块，含旧 FS 假设下 CPU RAM 64→32 KiB 的 16 块。本轮先撤下这项，保留其余五项约 **29 块**的待验证目标。
- 若后续仍能缩到 48 KiB，可再争取约 8 块；32 KiB 则必须在 HS 固件、栈和业务压力测试通过后才计入。
- 新 HS 包缓存需单独预算，并扣除被替换的旧 FIFO 后按实际网表计算净增；不能把 8–16 KiB 直接当成新增量，更不能把 25K FIFO 加到 138K。
- 当前 CNN 特征缓存 32→20 的 bank 重排目标仍独立成立；4 Hz 输出本身不兑现这 12 块，也不替代该实现。
